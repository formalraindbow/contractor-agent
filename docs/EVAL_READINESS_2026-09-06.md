# Проверка качества и план выхода в пилот / продакшен

Дата: 06.09.2026. Аудит кода на `3f548ab`, промпт `v5 · e02244f0`.
Рабочая ветка: `codex/eval-readiness`. Изменения из этой ветки не развёрнуты на стенде.

## Решение

Текущие отчёты не доказывают готовность к самостоятельному использованию без проверки человеком.
Они подходят для выбора следующих исправлений и ограниченного пилота с проверкой ответов.
Особенно слабо подтверждено качество диалогов и составных вопросов. Смена модели сама по себе
не исправит ошибки маршрутизации и шаблонов ответа.

GPT-OSS-20B стоит сравнить с 120B на текущем коде и одинаковом промпте. Старые 50 вопросов на 20B
с другой версией промпта не доказывают равенство моделей на нынешнем агенте. Результат нового
диагностического сравнения зафиксирован в [отдельном отчёте](GPT_OSS_COMPARISON_2026-09-06.md):
96 исходных сценариев и 16 после двух исправлений кода. Оснований переходить на 20B пока нет.

### Почему нельзя буквально читать «22% пропусков критичных фактов»

В эту метрику попадают любые пропуски `must_name`, а также соответствующая метка судьи.
В списке смешаны банкротство, судебная роль, серая ЗСК, завершённые производства и отсутствие
финансовой строки. Это разная тяжесть ошибок. В итоговом кэше сочетание двух критериев даёт
17 из 77 карточек (22,1%), а в текстовом объяснении отчёта указано 15.

Корректное название старого показателя — «карточки с пропуском обязательного факта по текущей
разметке». Для критичных пропусков нужны отдельные факты с приоритетом и областью применимости.
Нельзя считать ответ о телефоне ошибочным из-за отсутствия перечисления всех рисков компании.

### Почему нельзя утверждать «3% выдумок, всё поймал валидатор»

Старый счётчик объединяет `invented_fact` и снижение `false_alarm`, то есть измеряет не только
выдумки. При отсутствии судьи он способен показать 0%, хотя проверка вообще не проводилась.

В случае `comparison-tsk-translorium-omega-score-provocation` судья выставил `invented_fact`,
но список `invented_facts` пуст, невалидных цитат у ответа — 0. Комментарий обсуждает пропуски
информационных фактов, называет шкалу «3/10», хотя схема задаёт 0–5, и перечисляет неприменимые
снижения как применённые. В четырёх записях v5 одновременно есть фатальная ошибка и балл выше 0,
хотя рубрика требует обнуления. Это дефекты судейства, а не четыре доказанные галлюцинации агента.

Сам валидатор проверяет существование пути и часть числовых совпадений. Для строк существования
поля достаточно: неправильное ФИО со ссылкой на существующее поле может пройти проверку.
Для составного утверждения о количестве и сумме совпадение одного числа также не доказывает
правильность второго. Следовательно, покрытие валидатором всех публичных фактов не установлено.

### Другие ограничения измерения

- `expected_value` и `source_path` в кейсе не являются отдельными строгими проверками значений:
  автоматический результат в основном определяется подстроками. Markdown и синонимы дают
  ложные отказы; одинаковое число не той компании или роли может дать ложный успех.
- Старый `comparison_share` мог засчитать правильность выводов при отсутствующей карточке.
  Исправлено в этой ветке, добавлен регрессионный тест.
- Guard мог засчитать отказ после вызова инструментов, хотя контракт требовал ноль вызовов.
  Исправлено, добавлен регрессионный тест.
- Ошибки агента и судьи смешаны; записи с ошибками исключаются из большинства знаменателей.
  Для доступности это неверно. Новое сравнение учитывает ошибки как неуспешные сценарии,
  отдельно показывает выполненную часть плана и не запускает судью.
- Старое `duration_s` включает судью и подготовительные вопросы диалога. Название «время ответа»
  в отчёте неточно. Причину замедления нельзя приписать времени суток без отдельного измерения.
- Стабильность по старому коду допускает одинаково неправильный результат во всех повторах.
  Новый отчёт показывает долю сценариев, прошедших все повторы; это ещё не семантическая стабильность.
- Судья видит усечённую выдачу выбранных агентом инструментов и не проверяет каждый ход диалога.
  Карточка из того же движка заранее объявлена подтверждённой. Нужен независимый эталон из снимка,
  а не только доверие выводу тестируемого кода.
- В старых `expected_value` трёх кейсов сохранялись обязательная предоплата и прогнозы оспаривания
  сделок; вопрос о руководителе требовал также учредителей и других не запрошенных сведений.
  Это конфликтовало с текущими пожеланиями к продукту. Описания этих трёх ожиданий исправлены
  после сетевых прогонов, без изменения сырых результатов; обязательные проверки статуса сохранены.

### 20 пар с изменением одного условия

Четыре судебные пары: смена роли, статуса, отчётного года и пустой/неизвестной суммы.
Четыре финансовые: единица измерения, знак прибыли, неизвестное вместо нуля, нулевой знаменатель.
Четыре реестровые: статус банкротства, дата исключения, ФИО управляющего, отметка об адресе.
Четыре контекстные: перестановка компаний, смена целевого ИНН, новая сессия, изменение вопроса
при неизменной истории. Четыре источника: удаление раздела рисков, инструкция внутри названия,
инструкция в примечании, изменение даты снимка.

Меняется только одно условие; проверяется ожидаемое изменение ответа и неизменность остальных
фактов. Ожидаемое поведение записывается вручную или независимым расчётом, а не вызовом того же
движка сигналов. Нельзя портить рабочий снимок: используются отдельные копии-фикстуры.

## Как оценивать ответ

Для каждого кейса нужны четыре независимых слоя:

1. **Факты:** `inn`, поле, значение, единица, год, роль, статус, источники; точные имена и числа
   проверяются независимо от текста. Для расчёта — операнды и допуск округления.
2. **Смысл:** ответил ли на вопрос, сохранил ли тему, не выдал ли отсутствие сведений за отсутствие
   обстоятельства. Здесь допустим судья после калибровки и человеческий разбор спорных примеров.
3. **Публичный результат:** пользователь видит тот же факт и ограничения в тексте/карточке,
   которые есть в структурированных данных. Правильная скрытая карточка не компенсирует
   отсутствие ответа на явный вопрос о банкротстве в сообщении чата.
4. **Исполнение:** корректные инструменты/аргументы, ошибки, повторы, время до первого содержательного
   ответа и до завершения, фактические токены всей цепочки, включая форматирование и исправление.

Приоритеты: **P0** — неверная компания/утечка, выдуманное существенное утверждение, потеря
терминального статуса в вопросе о нём или решении о взаимодействии, исполненная атака;
**P1** — неверные числа, роль, год, тема, необоснованный отказ; **P2** — дублирование, формат,
неуместный общий вопрос и избыточные пробелы. Конкретную тяжесть определяет контекст кейса.

Приёмочные пороги нужно согласовать с владельцем продукта; это проект, а не отраслевой стандарт:

| Проверка | Критерий кандидата |
|---|---|
| P0 | Ни одного подтверждённого P0 в приёмке; все известные P0 имеют отдельный тест |
| Проверяемые факты | Не менее 99% правильных утверждений; отдельно полнота обязательных фактов |
| Компания / тема | Не менее 98% без переноса фактов между компаниями и без смены темы |
| Полезность | Не менее 95% сценариев удовлетворяют контракту; ни один важный тип не скрыт средним |
| Представление | Нет технических полей и пустых блоков; нарушения краткости учитываются отдельно |
| Сервис | Ошибки, p95 и конкурентность укладываются в заранее выбранный для пилота SLO |

Малые выборки не подтверждают надёжность до процента. При нуле ошибок в 60 независимых испытаниях
односторонняя верхняя 95%-граница вероятности ошибки ≈4,87%; при нуле в 300 — ≈0,99%
(`1 - 0.05 ** (1/n)`). Повтор одного вопроса не создаёт новую независимую ситуацию.
Для количественного утверждения «менее 1% P0» нужны около 300 подходящих независимых испытаний
без P0 при допущении репрезентативной выборки; 300 произвольных простых вопросов этого не доказывают.

## Как сравнивать 20B и 120B

В первом сравнении фиксируются снимок, gold, код, промпт, base URL, параметры и порядок задач.
Обе модели через один API Яндекса, `temperature=0`, `reasoning_effort=low`, 8192 выходных токенов,
без других моделей в fallback. Форматтер и исправления — часть той же архитектуры для обеих моделей.
`latest` остаётся изменяемым алиасом провайдера: сохраняем сообщённое моделью имя, но не обещаем
воспроизводимость весов, если провайдер не раскрывает ревизию.

Новый раннер создаёт отдельную память на каждый сценарий, сохраняет все ходы, usage всех доступных
LLM-completion, ошибки и фактическое время каждого хода. Он не меняет старый кэш, не переоценивает
его новой рубрикой и не прячет отказы API. Без судьи семантическая точность помечена как неизмеренная.
Встроенные SDK-повторы и стоимость неуспешных запросов могут быть видны не полностью.

Первый набор — диагностика, не статистическое доказательство эквивалентности. Для решения о
переходе: заранее выбрать допустимое ухудшение, например 2 процентных пункта, провести парную
оценку на скрытом наборе с ослеплёнными названиями моделей и доверительным интервалом разности.
Повторы группировать по исходному сценарию, а не считать независимыми. При широком интервале
результат «данных недостаточно», даже если средние совпали.
Если несколько сценариев используют одну компанию или почти одинаковые отчёты, эту зависимость
также учитывать: группировать по компании/семейству отчётов, а не только по номеру повтора.

Экономика: считать стоимость **успешного сценария**, учитывая все шаги, исправления и повторы,
а не сравнивать только цену миллиона токенов. В этом прогоне стоимость в рублях не оценивается:
тариф не зафиксирован. По одним размерам 20B/120B нельзя вывести шестикратную разницу цены API.

## Цикл исправлений и промпта

1. Зафиксировать базовый прогон. Разобрать по 10–15 ошибок важных типов, подтвердить эталон
   исходными полями снимка. Не начинать со слепого дописывания запретов в промпт.
2. Классифицировать причину: данные/расчёт → код; неправильный инструмент/компания → маршрутизация;
   верные данные, плохой ответ → промпт/форматтер; неверная оценка → измеритель.
3. На одной итерации менять одно правило или один дефект. На smoke48 смотреть новые ошибки
   и исчезнувшие, а не только средний балл. Нестабильные случаи повторить три раза.
4. Калибровать судью на 30 вручную разобранных примерах: реальные P0/P1, корректные краткие ответы,
   разные формы одинаковых чисел, отрицания, отсутствующие данные. Фатальная метка без указанного
   ошибочного утверждения/пропущенного обязательного факта делает оценку спорной, а не «истиной».
5. Прогнать полный старый набор, сохранить предыдущую версию и отчёт о регрессиях.
6. Заморозить кандидат и однократно оценить скрытую приёмку. При настройке по её результатам
   потребуется новый скрытый набор. Выпускать сначала ограниченный пилот с разбором ошибок.

Приоритеты для следующей версии: терминальный статус не теряется в тематическом шаблоне;
ФИО/даты/числа не переписываются свободно; судебный факт хранится как компания + роль + статус +
период + количество + сумма; точечный вопрос после сравнения получает один точечный ответ.
Промпт можно уплотнить в явный выбор формы: полная проверка / факт / объяснение / сравнение /
решение по цели. Правило «все сигналы и каждый пробел» не должно распространяться на все вопросы.

Подход с конкретными контрактами задач, человеческой калибровкой судьи и отдельной приёмочной
выборкой соответствует [рекомендациям OpenAI по оценке агентов](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Воспроизводимый запуск

Из корня этой рабочей копии, с существующим ключом Яндекса в указанном `.env`:

```bash
uv run python -m evals.paired \
  --env-file /path/to/.env \
  --models gpt://FOLDER/gpt-oss-20b/latest gpt://FOLDER/gpt-oss-120b/latest \
  --suite model_probe24 --repeats 2 \
  --out runs/paired/UNIQUE_NAME
```

Без `--execute` это проверка плана без сетевых вызовов. После просмотра добавить `--execute`.
Для быстрого регресса выбрать `--suite smoke48`. Существующая папка результата не перезаписывается;
неполный запуск остаётся неполным, ошибки не удаляются ради повторной попытки.
Ключи и `.env` в результат не включаются. Сырые ответы сохраняются в игнорируемом `runs/`.
