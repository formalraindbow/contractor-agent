# Хранение диалогов

В развёртывании чаты хранятся в PostgreSQL, отдельно от API-подов. Идентификатор
`thread_id` связывает сообщения, выбранные ИНН, цель проверки, уточнения, карточку
ответа и основания. Новый экземпляр приложения читает это состояние из той же
базы; sticky sessions не требуются. В браузере идентификатор остаётся в ссылке
`?chat=…` и sessionStorage.

`SESSION_STORE=postgres` выбирает постоянное серверное хранилище. Это значение
также задано по умолчанию в Docker-образе, чтобы контейнер не начал писать чаты
на свой временный диск при пропущенной настройке.
`SESSION_DATABASE_URL` — секрет с DSN PostgreSQL. Приложение **не переходит в память
или SQLite**, если база недоступна: запуск завершается ошибкой, а работающий API
перестаёт проходить readiness и возвращает 503 на новые запросы. DSN не возвращается
в API. `/v1/live` проверяет процесс, `/v1/ready` — доступность хранилища; обе пробы
возвращают только статус и не требуют пароля страницы.

Перед первым запуском и при обновлении версии checkpointer нужно выполнить:

```bash
uv run kontragent-db-init
```

Команда создаёт таблицы и применяет миграции LangGraph. Она идемпотентна; параллельные
запуски сериализуются блокировкой PostgreSQL. API сам DDL не выполняет и проверяет
версию схемы при старте. Соединения работают в autocommit, состояние десериализуется
с явным списком разрешённых типов, без pickle fallback.

Два экземпляра API не могут одновременно менять один разговор: advisory lock
удерживается до завершения/отмены ответа. Второй запрос получает 409. Для блокировки
выделяется отдельное соединение, которое закрывается по завершении запроса; оно не
занимает пул записи checkpoints. Разные чаты обрабатываются независимо. Учитывайте
при расчёте лимита соединений: до `SESSION_POOL_SIZE` (по умолчанию 5) на экземпляр
плюс одно на каждый активный ответ. Нужен прямой PostgreSQL или PgBouncer в режиме
session pooling; transaction pooling несовместим с session advisory locks.

При штатном завершении соединение с блокировкой закрывается сразу. После аварийного
разрыва сети блокировка освобождается, когда PostgreSQL обнаружит потерю соединения;
это не обязательно мгновенно. TCP keepalive настроен для таких соединений.

## Docker Compose

В `.env` задайте `POSTGRES_PASSWORD` и DSN с тем же паролем:
`SESSION_DATABASE_URL=postgresql://contractor:<URI-encoded-password>@postgres:5432/contractor`.
Ключ и модель Yandex остаются в прежних переменных. Затем:

```bash
docker compose up --build -d
```

Compose поднимает PostgreSQL с именованным томом `sessions-postgres`, запускает
миграцию и только после её успеха запускает API. Пересоздание API-контейнера не
затрагивает базу. Обычный `docker compose down` сохраняет том. `down -v` удаляет его
вместе с чатами — эту команду не использовать для обычного перезапуска.

Том обеспечивает сохранение данных на этом Docker-хосте, но не заменяет резервное
копирование и отказоустойчивость базы. Для нескольких хостов используется внешняя
PostgreSQL; пример Kubernetes ниже не разворачивает базу внутри API.

## Kubernetes

В `deploy/kubernetes/` подготовлены Job миграции, Deployment с двумя репликами и
Service. Перед применением замените `contractor-agent:review-v4` на тег образа в
вашем registry и создайте Secret `contractor-agent` штатным менеджером секретов.
Secret содержит `SESSION_DATABASE_URL` внешней базы с TLS, `YANDEX_API_KEY`,
`LLM_MODEL`, при необходимости `WEB_PASSWORD` и остальные настройки провайдера.

```bash
kubectl apply -f deploy/kubernetes/db-init.yaml
kubectl wait --for=condition=complete job/contractor-db-init --timeout=300s
kubectl apply -f deploy/kubernetes/app.yaml
kubectl rollout status deployment/contractor-agent
```

При следующей версии миграции используйте новое имя Job (или удалите завершённый
Job перед повторным созданием). После rollout можно удалить один API-под и открыть
прежнюю ссылку чата: новая реплика прочитает его из той же БД. Манифесты подготовлены
как пример запуска; кластера Kubernetes в этом окружении нет.

## Локальные диалоги и проверка

Запуск без Compose по умолчанию остаётся на SQLite (`SESSION_STORE=sqlite`).
Путь задаётся `SESSION_DB_PATH`, иначе это `RUNS_DIR/sessions.sqlite3`. На стенде
8082 используется `runs/comparison-servers/review-v4/sessions.sqlite3`: уже созданные
диалоги сохранены. Исходный `develop` на 8081 остаётся контрольной версией.
SQLite подходит для локального запуска одним процессом; его нельзя размещать
на временном диске пода. `SESSION_STORE=memory` — явно временный режим.

Переключение существующего стенда на другую пустую базу само по себе **не переносит**
старые диалоги. Сначала нужен перенос с резервной копией и сверкой состояний; не
меняйте DSN работающего стенда, рассчитывая на автоматическую миграцию SQLite.

Интеграционные тесты работают с настоящим PostgreSQL и создают отдельную временную
БД на каждый тест. У тестового пользователя должно быть право `CREATEDB`:

```bash
TEST_POSTGRES_URL='postgresql://test-user:password@localhost/postgres' uv run pytest -m postgres
```

Проверяются новый экземпляр с пустой локальной папкой, история и продолжение без
повторного ИНН, два параллельных API, 409 при записи в один чат, отмена запроса,
`SIGKILL` отдельного процесса, повторная миграция и отказ базы без перехода в память.
Без `TEST_POSTGRES_URL` эти тесты явно пропускаются, обычные тесты SQLite выполняются.

Проверка 05.09.2026: PostgreSQL 15.13 в отдельном локальном кластере; основной
набор — 258 тестов успешно, после дополнительной защиты раннего отключения SSE
повторно пройдены 16 тестов API/сессий (включая новый тест). Собран wheel, выполнены
Ruff и `docker compose config --quiet`; YAML Kubernetes прочитан и проверен на
структуру ресурсов. Docker daemon недоступен, контейнеры и Kubernetes-поды здесь
не запускались. Прикладные проверки PostgreSQL используют заданные ответы модели
и реальные MCP-инструменты: дополнительных платных запросов к Yandex нет.

Постоянное хранение не добавляет систему аккаунтов: UUID чата не заменяет проверку
его принадлежности пользователю. Для банковского развёртывания отдельно нужны
авторизация владельца, политика хранения/удаления, резервное копирование и проверка
восстановления PostgreSQL.

Основа реализации — [PostgreSQL checkpointer LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence)
и [официальная процедура setup](https://reference.langchain.com/python/langgraph.checkpoint.postgres/aio/AsyncPostgresSaver/setup).
