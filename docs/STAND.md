## Локальный запуск

```sh
uv sync --frozen
# Один раз: скопируйте .env.example в .env и задайте ключ провайдера и модель.
uv run kontragent-api --host 127.0.0.1 --port 8080
```

В `.env` задаются `LLM_BASE_URL`, `LLM_MODEL`, ключ провайдера и `WEB_PASSWORD`.
Пароль обязателен для общего стенда. Он используется существующим входом по ссылке
с параметром `k` или HTTP Basic с логином `alfa`.
Ключи модели и пароль не коммитятся. `/v1/health` после входа показывает выбранную модель.

Локальный путь базы задаёт `SESSION_DB_PATH`; у старого запуска на 8084 использовался
`.cache/review-develop.sqlite`. Этот путь отличается от базы VPS, указанной выше.
Не удаляйте файлы диалогов при обновлении кода.

## Исторический вариант: доступ через Pinggy

Для общего стенда туннель больше не используется. Ниже сохранён запасной способ
временного показа локального приложения.

После запуска приложения, в отдельном терминале:

```sh
ssh -o StrictHostKeyChecking=accept-new -o ServerAliveInterval=30 \
  -o ExitOnForwardFailure=yes -p 443 -R0:localhost:8080 -T free.pinggy.io x:https
```

Используйте HTTPS-адрес из вывода текущего процесса и добавьте ключ доступа `k`.
При первом открытии в браузере Pinggy показывает свою страницу: нажмите **Enter site**.
В Chrome при проверке первый переход иногда завершался `ERR_SSL_PROTOCOL_ERROR`;
повторное открытие той же ссылки проходило, дальше карточка и F5 работали штатно.
При ошибке соединения в Safari попробуйте второй HTTPS-адрес того же процесса:
Pinggy также выводит домен `*.run.pinggy-free.link`. На телефоне проверяющего
этот адрес открылся, когда основной `*.free.pinggy.net` был недоступен.
Бесплатный туннель действует 60 минут; новый запуск выдаёт новый адрес.
Запуск приложения и SSH должны оставаться активными, компьютер — включённым.
Проверяйте вход, получение карточки и один ответ агента через внешний адрес.
Актуальные адреса на машине стенда записываются в игнорируемый Git файл `runs/links.txt`.

## Запасной доступ через localhost.run

Если Pinggy не открывается, можно подключить другой туннель к тому же приложению:

```sh
ssh -T -o StrictHostKeyChecking=accept-new -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -R80:127.0.0.1:8080 nokey@localhost.run -- --output json --inject-http-proxy-headers
```

Используйте выданный HTTPS-адрес и существующий ключ доступа `k`.
Параметры описаны в [документации localhost.run](https://localhost.run/docs/cli/).
Это также временный адрес: приложение и SSH должны оставаться запущенными.
Другой домен не переносит браузерный список проверок; серверная база диалогов остаётся той же.

05.09.2026 через этот туннель проверены первый вход без дополнительных заголовков,
карточка, ответ агента через SSE и восстановление диалога после обновления страницы
в Chromium с размером экрана iPhone 13. Это не заменяет проверку настоящего Safari.
Вход по ключу теперь перенаправляет на относительный URL: схема HTTPS сохраняется,
даже если прокси передаёт приложению HTTP и не сообщает исходную схему запроса.
Тесты входа проверяют удаление ключа из URL, сохранение параметра чата и вход по cookie.
