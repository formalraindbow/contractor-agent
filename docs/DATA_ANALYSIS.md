# Разбор данных — что нужно знать до первой строчки кода

Прогнаны оба файла выгрузки, 200 компаний, все поля. Здесь то, что нельзя
увидеть, открыв один пример: мины парсинга, дыры покрытия и готовые карточки
под демо и тесты.

---

## 1. Главное: готовые формулировки не покрывают всё, что лежит в данных

В отчёте есть секция `reputationalRisks` — 15–16 готовых текстов с рекомендациями
на карточку. Соблазн: агент их пересказывает. Проблема: **они не покрывают поле
`status.reasonName`**, а там лежат факты, ломающие сделку.

**ООО «МАКСМАРКЕТ»**, ИНН 5032257375:
- `riskLevel = LOW`, `zskRiskLevel = GREEN` — обе метки банка зелёные;
- `status.status = CURRENT` — действующее;
- `status.reasonName` = **«Юридическое лицо признано несостоятельным (банкротом)
  и в отношении него открыто конкурсное производство»**;
- 507 исполнительных производств, 54 активных · 278 арбитражных дел.

**ООО «РАДО АЛАТЫРЬ КС»**, ИНН 2100006761 — ещё чище как демонстрация:
- `LOW / GREEN`, **негативных признаков ноль**, `reputationalRisks.negative` пуст;
- `status.reasonName` = «Регистрирующим органом принято решение о предстоящем
  исключении юридического лица из ЕГРЮЛ».

Агент, который смотрит на метки и готовые формулировки, скажет по этой компании
«всё чисто». Компанию исключают из реестра.

**Всего таких карточек 6 из 200** — `status.reasonName` заполнен при статусе
CURRENT: банкротство · предстоящее исключение из ЕГРЮЛ (дважды) · смена места
нахождения (дважды) · уменьшение уставного капитала. Ни одна не помечена
красным, пять из шести — GREEN.

Вот это и есть ответ на вопрос «зачем агент, если рекомендации уже написаны».

## 2. Три мины парсинга — на них ляжет код, написанный по одному примеру

**Мина 1. Числа приходят то числом, то объектом.** MongoDB extended JSON:
```
"commonAmount": 957189                          // int
"commonAmount": {"$numberLong": "4534783044"}   // объект!
```
Так себя ведут 16 путей — суммы арбитража (включая `arbitrationCases[].defendantAmount`),
активы, пассивы, капитал (`liabilities.capitals`), выручка, `shareCapital`,
`cofounders[].amount`. Правило одно: обёртка у любого целого ≥ 2³¹, до 15 вхождений
на поле (`common.proceeds`). Демо пройдёт, приёмка упадёт.
**Нужен нормализатор на входе — по всему дереву, не по списку полей.** В CSV обёрток
нет: там все ячейки — строки, и мина другая — типизация по пути (ОКВЭД `31.0`,
ИНН с ведущим нулём).

**Мина 2. Часть чисел — строки.**
`executionProceedings[].amount` = `"517235.54"` (строка; ключа нет у 770 из 3873
производств, в том числе у 66 активных — у ЛЕ МОНЛИД у 33 из 45 активных).
Отсутствие суммы — не ноль.
`coefficient.profitability / solvency / sustainability` = `"0.5"`, `"1.04"`.

**Мина 3. Две несовместимые схемы дат в одном документе.**
```
"registrationDate": {"$date": "2024-01-14T21:00:00.000Z"}   // объект
"startDate": "2023-11-17"                                    // строка
```
`$date` — в `baseInfo`, `status`, `foundersInfo`, `executionProceedings`,
`licenses`, `relatedCompanies`, `reportDate`. Плоская строка — в `inspections`.
Все `$date` — московская полночь, но у 198 дат 1993–2014 годов время `20:00:00Z`
(UTC+4), а не `21:00:00Z`. Разбор — только через `zoneinfo("Europe/Moscow")`:
наивная UTC-дата съезжает на день назад у всех, «+3 часа» — у старых. Настоящая
дата — московская (при UTC-трактовке 1392 даты из 6603 приходятся на выходные,
при московской — 142), поэтому даты отчётов — 30.07–28.08.2026.

## 3. Схема плавающая — секции есть не у всех

Заполненность из 100 (JSON / CSV):

| Секция | JSON | CSV |
|---|---:|---:|
| `baseInfo`, `kindsOfActivityInfo`, `status`, `zskRiskLevel`, `reputationalRisks`, `reportDate` | 100 | 100 |
| `foundersInfo`, `taxSystem` | 75 | 75 |
| `finReports` (непустой; ключ у 75, `[]` у 8) | 67 | 69 |
| `relatedCompanies` | 61 | 65 |
| `executionProceedings` | 53 | 43 |
| `procurements` | 8 | 9 |
| `arbitrationByStatus` (непустой) | 48 | 61 |
| `arbitrationCases` | 44 | 57 |
| `inspections` | 30 | 29 |
| `coefficient` | 19 | 28 |
| `licenses` | 9 | 13 |
| `branchesInfo` | 2 | 6 |
| `phones` | 29 | 31 |

Внутри `baseInfo` тоже дыры: КПП — у 75 (у 25 ИП ключа нет), адрес — ключ у всех,
но у 25 ИП пустая строка, `companySize` — 59, email — 35, **сайт — 11**.

«Секции нет» и «секция есть, но пуста» — разные состояния: `executionProceedings: []`
у 47, `phones` у 71, `procurements` у 92, `negative` у 42, `finReports: []` у 8
(включая ЛЕ МОНЛИД). CSV этого не различает — нужна явная политика присутствия.

⚠️ `arbitrationCases` — **не список дел**, а разбивка по годам:
`{year, plaintiffCount, plaintiffAmount, defendantCount, defendantAmount}`.
Отдельных дел с номерами в данных нет вообще.

⚠️ Агрегат и разбивка расходятся по присутствию у 12 из 200 (JSON 6+2, CSV 4+0).
Там, где есть оба (99), сводка больше суммы по годам у 55 — это окно: разбивка
только за 2023–2026. Реальных расхождений 5 плюс 22 дела без ролей внутри сводки.
У ДСА (7838104498) единственное дело как ответчик видно только в разбивке.

## 4. Знак признака задаёт секция, а не код

После нормализации кириллической «а» все 12 негативных кодов JSON встречаются
и в `positive`:
```
positive: {"code": "fnsBlocking", "name": "Нет блокировок банковских счетов..."}
negative: {"code": "fnsBlocking", "name": "Есть блокировки банковских счетов..."}
```
Матчинг по `code` без учёта секции даст ровно противоположный ответ.
Коды: `fnsBlocking`, `massAddress`, `massOkved`, `invalidAddress`,
`invalidRegistrationData`, `liquidationStatus`, `executionProceedings`,
`profit`, `currentAssets`, `massAuthpersons`, `invalidAuthpersonsData`.
Словарь открытый: в CSV-наборе негативные `dishonestProvider`, `taxArrears`,
`inspectionWithViolation` (по одной компании), которых в JSON нет; в объединении 15.

## 5. Объём: карточка не влезает в промпт целиком

**ООО «ЛЕ МОНЛИД»**, ИНН 5029069967 — **1744 исполнительных производства
и 1525 арбитражных дел**, при этом `riskLevel = UNKNOWN`, `zsk = GREEN`.
**ООО «МАКСМАРКЕТ»** — 507 производств.

Подавать такие карточки в модель целиком нельзя. Нужна агрегация до подачи:
свернуть производства в «активных N на сумму X, завершённых M», а полный список
отдавать только по явному запросу.

## 7. Что из этого следует для агента

1. **Читать `status.reasonName`** — там банкротство и исключение из реестра,
   и в готовых формулировках этого нет.
2. **Нормализовать вход** до подачи в модель: `$numberLong` → int по всему дереву,
   строки-суммы → `Decimal`, обе схемы дат → `date` через `Europe/Moscow`.
3. **Различать «нет данных» и «нет факта».** Секции отсутствуют у большинства:
   «лицензий нет» — неверно, «сведений о лицензиях в отчёте нет» — верно.
4. **Не складывать активные и завершённые производства.** У «БИЛД-ЮГ» два
   производства, активно одно, и у активного суммы в данных нет вообще.
5. **Агрегировать до подачи** — иначе «ЛЕ МОНЛИД» съест весь контекст.
6. **Знак признака брать из секции**, не из кода.
7. **Показывать дату отчёта** — они разные, от 30.07 до 28.08 по Москве.
